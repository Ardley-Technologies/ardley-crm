# W6 scope — the real principal extractor

Plan: [`poc-plan.md`](poc-plan.md) §8 ("Cognito pools to reuse", "Acorn store"). Goal: a
principal resolved the way the rest of the platform resolves one, so any Ardley customer and
any SSO user works — not just two hardcoded tenants with a password.

## What the BFF actually does today

Established by reading the code and querying dev, not from the plan:

- `customerIdFromClaims` ([`handler.mjs:102`](../infra/lambda/bff/handler.mjs)) reads
  `custom:customerId` / `custom:tenantId` off the ID token and returns `null` unless the
  value is a key in a hardcoded `TENANTS` map holding `100004` and `100081`. A valid token
  for any other Ardley customer gets `403 unknown_principal`.
- No DynamoDB read anywhere. The Lambda has no IAM for those tables.
- `iss` is pinned to the dev platform pool (`handler.mjs:77`). The CRM app client's
  `SupportedIdentityProviders` is `["COGNITO"]`, and the dev platform pool has **zero**
  identity providers — so no SSO identity can reach it.
- `crm_users.contact_id` is never written, so invariant 1 holds only for seeded users.

That is a POC shortcut, not the architecture. §8 is the architecture.

## Target

Resolve tenant + role in the platform's order:

1. **Claims.** `custom:customerId` / `custom:tenantId`, plus role when present. Platform
   pools inject `custom:customerId` at token issuance via a pre-token-generation Lambda that
   reads membership, so an SSO user usually arrives already enriched and never needs a table
   hit on that request.
2. **Authz store.** `ardley-role-configurations-{env}`, keyed `[tenantId, roleId]`, when
   claims carry a tenant but no role.
3. **Membership fallback.** `ardley-customer-users-{env}`, pairing `sub` or email → customer
   id, for password users and un-enriched tokens.

`tenant_id` for Acorn is the **Ardley customer id string**; Postgres uses
`tenants.id = uuid5(uuid5(DNS, 'ardley-crm.tenants'), customer_id)`. The BFF maps between
them at the boundary.

## Workstreams

### W6.1 — De-hardcode tenancy · DONE

Decided: **auto-provision** the tenant row on first sight, so any Ardley customer
resolves to an empty, correctly isolated CRM rather than a 403. §8's "CRM tenants are
projections, not a third allow-list" is the reason; the cost is that the CRM now
accepts every customer id a valid token can carry.

Shipped in `infra/lambda/bff/tenant.mjs`, imported by both the Lambda and the local
stub so they cannot drift (the Lambda asset bundles its whole directory; the CDK asset
excludes `*.test.mjs`). `TENANTS` is gone from the deployed handler; `KNOWN_SLUGS`
remains as cosmetics only.

Verified on local Docker: `100033` — a customer with no seed data — resolves to
`23f2393b-…`, auto-creates `customer-100033`, and sees **0 contacts**. `100004` still
sees 178 and `100081` still sees 5, on their original UUIDs. Non-numeric and
injection-shaped ids get 403. All five isolation smokes pass.

A new `bff` Vitest project covers `infra/lambda/**` and `server/**`; the seven tests
pin the derivation to the seeded fixtures, assert agreement with
`scripts/tenant_uuid.py` by running it, and check an RFC 4122 worked example so a
broken hash is caught independently of our own values. The `app` project needed an
explicit `src/**` include, since the default glob otherwise dragged these Node-only
suites into the browser runner.

### W6.1 original scope · no new dependency

Replace the `TENANTS` map with the derivation. Verified in Python that
`uuid5(uuid5(DNS, 'ardley-crm.tenants'), customer_id)` reproduces both seeded UUIDs
(`100004` → `4b51bd26-…`, `100081` → `28dd4130-…`) and generalises (`100033` →
`23f2393b-…`), so no lookup is needed for the UUID — it is a pure function.

`uuid` is not a dependency and the BFF Lambda declares none, so implement uuid5 (SHA-1) in
~12 lines with `node:crypto` rather than adding a package. Testable locally against the stub
header; needs neither Acorn nor SSO. **This is the piece that stops "two tenants" being
baked in, and it is the cheapest.**

### W6.2 — Membership fallback · unblocked, needs IAM

`ardley-customer-users-dev` items are `{customerId, emailAddress, userId}` with GSIs
`email-address-index` and `customer-id-index`. **`userId` is a 32-char hex string, not a
Cognito `sub`** — sampled one to confirm — so the join has to be by `emailAddress`. §8
sanctions that ("`sub` (or email)"), but email is mutable, which is risk #7 territory:
persist the resolved customer id on `crm_users` so the lookup is once per user, not once per
request.

Needs a Dynamo `Query` grant on the table and both GSIs. Note `customerId=100004` has 36
member rows in dev; **`100081` has zero**, so this path cannot resolve Envoy on dev until
membership is seeded there.

### W6.3 — Acorn evaluation · blocked

`@ardley-technologies/acorn-lambda` is not on the public registry and no `.npmrc` configures
a private one. `ardley-role-configurations-dev` keys on `CUSTOMER#<id>` / `ROLE#<id>`, and a
300-item sample contains **zero** `Crm*` actions — so the POC seed of CRM actions and roles
described in §8 has not happened either.

Deferring this does not break the isolation story: invariant 4 already says "Acorn decides
who may act; Postgres only isolates tenants", and RLS on `tenant_id = current_tenant()` is
what enforces isolation. What is missing without it is action-level authz (who may merge, who
may edit whose records) — currently nothing enforces that server-side.

### W6.4 — SSO is an environment problem, not a code one

Dev has no identity providers **by design**. Confirmed against AWS:

| env | platform pool | IdPs |
|---|---|---|
| dev | `us-east-1_m3IX8Cc9L` | none |
| test | `us-east-1_nIneVR5Wf` | `envoy-sso-azure`, `woodley-sso-azure` |
| demo | `us-east-1_MErm7hWed` | none |
| prod | `us-east-1_UFnHNuW7a` | `envoy-sso-azure` |

So "log in with my Envoy SSO user" means **deploying the stack to test** and adding a CRM app
client to `us-east-1_nIneVR5Wf`. Because those pools enrich the token, tier 1 alone should
resolve the tenant — W6.2 is not a prerequisite for SSO.

Also worth holding onto: `EnvoyMortgage-user-pool-dev` (`us-east-1_2uUrt8450`) is Envoy's
**consumer/employee app** pool. §8 says CRM ignores it — do not attach CRM to a customer's
own pool or federate it in. It also has no custom attributes at all.

Per §8 the customer walkthroughs are meant to happen on **demo**, and test is where SSO can
be shown. Those are two different environments, so "demo the walkthrough" and "demo SSO"
cannot currently be the same session.

### W6.5 — Invariant 1, adjacent and cheap

Populate `crm_users.contact_id` once a principal resolves. The column and FK already exist
and the seed fills it for the Woodley LO; only the runtime path skips it.

## Decisions needed before implementing

1. **Unknown customer id.** A token resolves, say, `100033`, but no `tenants` row exists and
   FKs require one. Auto-provision the tenant row, or 403? Auto-provisioning makes the CRM
   accept any Ardley customer with no data; refusing keeps it to seeded tenants.
2. **Join key.** Accept email as the membership join, or get `sub` onto those rows first?
   Email works today and is sanctioned; it is also the mutable option.
3. **Which environment first** — test, because SSO exists there, or demo, because §8 says
   walkthroughs belong there?
4. **Acorn registry access.** Who can grant it, and is action-level authz in scope for the
   POC at all, or is RLS isolation enough for the meeting?
5. **No matching contact.** A resolved user has no `contacts` row: create one, or refuse?
   Invariant 1 says every human is a contact, so creating is the consistent answer.

## Order that gets value soonest

W6.1 is done. It was self-contained, needs no dependency or environment change, and removes the
hardcoded two-tenant ceiling. W6.4 next if the goal is showing SSO to Jesse, since it is
configuration rather than code and does not depend on W6.2. W6.2 after that, W6.5 alongside
it, and W6.3 whenever the registry access lands.
